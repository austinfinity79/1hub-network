# ADMIN-PROD-06-modules

**Evidence 4 – 8: Verification, Venture Review, Organization Access, Feedback, Categories.** Parent: [ADMIN-PROD-06-frontend.md](ADMIN-PROD-06-frontend.md).

> **Superseded in part (ADMIN-PROD-07-CONTRACT-FIX):** revoke authority is now exact-unit only ([DEC-ADM-D02](../../decisions/DECISION_LOG.md#dec-adm-d02)); `account:escalate` and the leader account-request route are withdrawn ([DEC-ADM-D04](../../decisions/DECISION_LOG.md#dec-adm-d04)). Historical evidence below is kept as recorded.

## 4. Role Verification UI — `/ops/admin/verification[/:id]`
Queue: status filter (PENDING default, APPROVED, REJECTED, WITHDRAWN — the frozen four, no invented "ALL"), requester (PROFILE_DISCOVERY name), position, routing (+ the PD-1 fallback flag), submitted time; `counts.pending` in the subtitle. Detail: full position/period, routing, the requester's existing memberships/leadership at the unit, history, reject reason. Approve / reject send `{version, reason?}` with a fresh `Idempotency-Key`; reject's reason stays optional per contract. No self-approval control (`can_act` is server-computed and already excludes it). States: loading, empty, denied (403 → "Bạn không có quyền"), not-found (404, identical for unknown/foreign/malformed), a 401 mid-session routes to sign-in.

## 5 – 7. Venture Review UI — `/ops/admin/ventures[/:id]`
Queue: status, kind (FIRST_PUBLISH / CORE_CHANGE), proposed name, owner, count of changed fields, submitted time. Detail renders the server's own `diff` array (`field, before, after`) through one small label/value formatter — **no generic document-diff engine was built**; vocabulary ids resolve to labels via the server's `vocabulary` map, never shown raw. The two columns are always headed "ĐANG CÔNG KHAI" (or "Chưa có phiên bản công khai" before a first publication) and "CHỜ DUYỆT": the pending candidate is never rendered under the public heading, and a first publication explicitly shows "no public version" rather than inventing a placeholder. `logo_asset_id` is pulled out of the generic diff row and shown as two side-by-side images (`logo.public`, `logo.proposed`) instead. Team membership is private, not a core field (DEC-ADM C2) — no team diff exists in the API, so none is drawn (the task's "team/member representation where relevant" has no relevant data here). Approve / reject: confirm via the same version-guard + reason flow as verification; after a decision the detail reloads from the server — no optimistic "approved" flash before the API confirms, and a stale-version 409 reloads instead of silently retrying.

## 8. Organization / Delegation UI — `/ops/admin/access[/:orgId]`
`/ops/admin/access` lists the units this actor's `access:delegate` reaches — PD-6: its own unit(s) plus their direct canonical children, every operational unit for PLATFORM_ADMIN (`listDelegationOrganizations`, `src/lib/admin/access-api.ts`, new — a read helper, not a new API route; see §9 below). It does **not** reuse `GET /ops/organizations`: that list is scoped by `network:read`, a capability a delegation-only grantee may lack entirely. `/ops/admin/access/{orgId}` is the real org-scoped screen: active grants, revoked history (`GET/POST …/access`, `GET …/access/history`, `POST …/access/{id}/revoke`, 05 §27/A10 unchanged), grant form (grantee profile id + capability — the **real** `CAPABILITY_MATRIX` filtered to `delegable: true`, never a hand-picked list) and revoke with an inline confirm. The frontend never computes who-may-grant-what: `can_revoke` and every grant's validity come from the server; a manipulated client request still gets the server's own refusal.

**Delegation safety (§10):** the form offers no upward or cross-branch target — it only ever grants on the one `orgId` already authorized for this actor, and the capability list is the frozen delegable set. **ADMIN-DECISION-02 guard:** `can_revoke` is `manager || granted_by === actor.profileId` (`access-api.ts`, unchanged by this task) — a co-leader (anyone else holding `access:delegate` on the same unit) can already revoke another leader's grant there; the UI shows the Revoke button exactly when the server says `can_revoke: true` and never narrows or widens that. This is reported, not resolved — ADMIN-DECISION-02 carries into PROD-07 unless the PO closes it first.

## 6. Feedback UI — `/ops/admin/feedback[/:id]`
Filters mirror the API 1:1 (`status, type, priority` incl. NONE, `owner` as a profile id, `created_from/to`); `counts.open` in the subtitle. Detail: content, sender (member name or "Khách"; guest e-mail shown only here), context reduced to the server's operator keys, screenshot, triage form (type, priority, owner, status, resolution note) in one PATCH. NEW → DONE without a note is refused by the server (422 `resolution_note: required`); the UI shows the same inline warning before submit, never hides it. DONE locks the status control (no reopen, matching the server). The weekly summary (`GET …/summary?week=`) is a read-only panel toggled from the queue header — total / by-type / by-priority / by-owner — not a separate analytics dashboard, and no per-item e-mail/Slack control exists.

**Screenshot retention UX (§13):** `screenshot.expired` (or a null url) renders one clean sentence ("Ảnh đã hết hạn lưu trữ…") — never a broken `<img>` tag, never the asset id or storage path.

## 9. Category UI — `/ops/admin/categories`
Six tabs (REGION, DOMAIN, SKILL, COUNTRY, SPECIALIZATION, VENTURE_STAGE), each: label (inline rename), archive/activate (absent for VENTURE_STAGE, matching `categoryChangeAllowed`), `in_use` count, and whole-type reorder via "move up/down" rather than drag-and-drop — no such library is in the stack, and the API either way takes the same full ordered id list (`PUT …/order`); this is a deliberate, documented substitution, not a missing feature. No category-type builder, no nested taxonomy, no generic config CMS.
