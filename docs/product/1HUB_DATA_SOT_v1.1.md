## 1. Data principles to freeze

1. **One individual → one root profile.** `IndividualProfile` is the canonical root for a person. Registrations, applications, memberships, startup/team memberships and activity records link back to it.
2. **Role is not identity.** Founder, HUB Member, Leader, Organizer, Investor, Representative… are relationships/role assignments with scope and lifecycle, not separate login identities.
3. **Entity histories are preserved.** Membership, leadership, representation, team/startup membership, programmes and profiles are ended/archived by state; historical records are not hard-deleted after activity exists.
4. **Profile data must carry provenance.** At minimum distinguish: `SELF_DECLARED`, `SYSTEM_RECORDED`, `ORGANIZATION_VERIFIED`, `IDENTITY_VERIFIED`.
5. **Visibility is independent from lifecycle and verification.** Visibility, verification, consent and role assignment are separate dimensions, never packed into one generic status.
6. **Sensitive access is consent-based.** Public discovery never implies access to contact, CV, deck, traction, funding or identity data.
7. **Programme/Event activity enriches existing entities.** Activity and outcome data generated by programmes/events link back to Individual, Project/Startup/Solution rather than creating isolated copies.
8. **Backend enforces permission and scope.** UI visibility is not a security boundary.
9. **Controlled vocabulary for searchable taxonomy.** Field, skill, stage, organization type, region and tag must use centrally managed dictionaries when used for filter/matching.

## 4. Canonical relationships and cardinality

```text
UserAccount 1 ───── 1 IndividualProfile

IndividualProfile 1 ───── * CommunityMembership * ───── 1 Organization
IndividualProfile 1 ───── * LeadershipRecord     * ───── 1 Organization
IndividualProfile 1 ───── * OrganizationRepresentation * ─ 1 Organization

Organization 1 ───── * OrganizationRelationship * ───── 1 Organization

IndividualProfile 1 ───── * TeamMembership    * ───── 1 Team
IndividualProfile 1 ───── * StartupMembership * ───── 1 Startup

Startup * ───── * Solution     via StartupSolutionRelationship
Individual/Team/Startup * ───── * Solution via contributor relationship

Programme 1 ───── * ProgrammeOrganizationRelationship * ───── 1 Organization
Programme 1 ───── * Event            [Event.programme_id nullable]
Programme 1 ───── * Application
Programme 1 ───── * Participation
Programme 1 ───── * Outcome

Application * ───── 1 PrimaryApplicant
PrimaryApplicant ∈ {IndividualProfile, Team, Startup}

Activity/Participation/Outcome → links back to related Individual / Team / Startup / Solution
```

### Relationship rules

- `CommunityMembership` and `LeadershipRecord` are separate records.
- `OrganizationRepresentation` is separate from Organization and from account identity.
- `StartupMembership` requires confirmation; never infer membership from founder text/badge alone.
- `Solution` can exist without a Startup.
- A Solution can preserve contributor history before/after it becomes linked to a Startup.
- Programme Organizer permissions are programme-scoped; they do not flow automatically from organization membership.
- Event can be standalone or nested under a Programme/Challenge.

## 5. P0 network-context decision

P0 onboarding must **not** convert a user's self-selected HUB/Chapter/CLB into an `ACTIVE CommunityMembership` automatically.

Allowed patterns:

1. **Preferred for 29/09 seed cohort:** pre-load/confirm existing membership + leadership from HUB's known roster, then link after account identification; or
2. Save user-declared affiliation as a **pending membership request** until Leader/Admin confirmation.

Do not introduce a new permanent `Affiliation` entity that bypasses the existing Membership/Leadership model unless BA explicitly changes the business rule.

## 6. Lifecycle / state SOT

### IndividualProfile
`NOT_CREATED → DRAFT → ACTIVE → DEACTIVATED`

### IdentityVerificationRecord
`UNVERIFIED → VERIFYING → VERIFIED | FAILED → REVERIFY_REQUIRED`

> Identity verification is a separate lifecycle and is not required by default in P0.

### CommunityMembership
`PENDING_APPROVAL → ACTIVE | REJECTED | WITHDRAWN → SUSPENDED / ALUMNI`

### LeadershipRecord
`ACTIVE → ALUMNI | REVOKED`

### Organization
`DRAFT → PENDING_CONFIRMATION → ACTIVE → VERIFIED_INFO / ARCHIVED`

> `verification_status` should be stored separately from operational profile status.

### OrganizationRepresentation
`PENDING_CONFIRMATION → ACTIVE → ENDED | REVOKED | REJECTED`

### Team / Startup membership
`PENDING_CONFIRMATION → ACTIVE → LEFT | REMOVED | REJECTED`

### Team / Startup / Solution profile
`DRAFT → ACTIVE → ARCHIVED`

### Programme / Challenge
`DRAFT → PUBLISHED → CLOSED → ARCHIVED`

### Event
`DRAFT → PUBLISHED → LIVE → ENDED | CANCELLED → ARCHIVED`

### EventRegistration
`REGISTERED → CHECKED_IN | CANCELLED | NO_SHOW`

### Application
`DRAFT → SUBMITTED → UNDER_REVIEW → NEEDS_UPDATE → RESUBMITTED → UNDER_REVIEW → CLOSED`

Later selection outcome may add `SELECTED | NOT_SELECTED` according to the programme phase.

### Access / Consent (future sensitive access)
`PENDING → APPROVED | REJECTED | WITHDRAWN | EXPIRED → REVOKED`

## 7. Data provenance SOT

Every profile fact that can influence trust/discovery should support provenance metadata.

### Source types

- `SELF_DECLARED` — user entered it.
- `SYSTEM_RECORDED` — produced by platform activity/event/programme.
- `ORGANIZATION_VERIFIED` — an authorized organization confirmed it.
- `IDENTITY_VERIFIED` — verified through identity infrastructure.

### Recommended logical metadata

```text
source_type
source_entity_type      # programme, organization, event, verification provider...
source_entity_id
recorded_at
recorded_by_role_assignment_id (when applicable)
verification_status     # only when verification is meaningful
```

`Timeline` is a presentation/read-model composed from canonical records; it should not become a second disconnected source of truth.

## 8. Visibility & consent SOT

### Visibility levels

1. `PUBLIC`
2. `NETWORK_ONLY`
3. `PROGRAMME_ACCESS`
4. `GRANTED_ACCESS`
5. `PRIVATE`

### Baseline classification

| Data class | Default |
|---|---|
| Display name, bio, role headline, field | PUBLIC |
| Public Startup/Solution/Organization data | PUBLIC |
| Detailed skills/experience/ecosystem links | NETWORK_ONLY |
| Programme/challenge operational data | PROGRAMME_ACCESS |
| Deep contact, CV, deck, traction, funding data | GRANTED_ACCESS |
| Registration email, phone, identity data, internal evaluation | PRIVATE |

### Consent record must capture

- subject / owner
- purpose
- data scope
- recipient / recipient organization when applicable
- consent policy/version
- granted_at
- expires_at when applicable
- revoked_at when applicable
- status

Consent is not a boolean on `UserAccount`.

## 10. Programme / Challenge modelling decision

### Proposed v1 decision

Use one logical `Programme` aggregate with `programme_type = PROGRAMME | CHALLENGE` for shared lifecycle, public detail, organizer relationships, applications and outcomes.

Challenge-specific concepts (e.g. problem statements / challenge owner pipeline) become child objects of a `CHALLENGE` programme, rather than duplicating the whole programme model.

**Reason:** Current business rules and state matrix treat Programme/Challenge together, while challenge introduces specialized content rather than a completely independent account/profile lifecycle.

This is a **proposed Data SOT decision** and should be explicitly accepted before physical schema design.

---

## 11. Event modelling decision

`Event` is an independent canonical entity with an optional parent programme relation:

```text
Event.programme_id = nullable
```

Therefore:

- standalone event → no programme parent;
- programme activity/event → references parent Programme/Challenge.

Do not model Event as merely an embedded JSON block inside Programme.

---

## 12. Application data principle

An Application must not duplicate the full applicant profile.

```text
Application
  ├── primary_applicant_type
  ├── primary_applicant_id
  ├── programme_id
  ├── status
  ├── programme_specific_answers
  └── submitted snapshot/version references where required
```

Profile reuse is canonical. Programme-specific answers are additional data only.

Exactly one primary applicant is allowed: `Individual`, `Team` or `Startup`.

## 13. Timeline / enrichment model

Long-term profile value is generated through linked activity, not manual copying.

```text
IndividualProfile / Startup / Solution
        ▲
        │ linked records
        │
Participation ─ Activity ─ Achievement ─ Outcome
        ▲
        │
Programme / Challenge / Event
```

The user-facing `Profile Timeline` should be derived from these canonical records with provenance and visibility applied.

## 15. Constraints / integrity rules for SA

1. Unique `IndividualProfile` per person/account identity.
2. No organization shared-login model.
3. No active membership created solely by self-declaration.
4. All scoped roles reference both actor and scope.
5. Soft-delete/archive historical business entities/relations after activity exists.
6. Sensitive access always evaluates visibility + role/scope + consent.
7. Programme/Event outcome records must keep source references.
8. Application profile reuse should use canonical entity references; avoid full data duplication.
9. Paginate large lists and logs.
10. Private files must not use permanent public URLs.

## D1 — Programme vs Challenge modelling

### Decision
Use **one canonical `Programme` aggregate** with:

```text
programme_type = PROGRAMME | CHALLENGE
```

`Challenge` is not a second root aggregate with duplicated lifecycle. Challenge-specific concepts become child objects of a `Programme` whose `programme_type = CHALLENGE`.

Examples of challenge-only children that may be added later:

- `ProblemStatement`
- `ChallengeTrack`
- `ChallengeOwnerRelationship`
- challenge-specific evaluation configuration

`Event` remains a separate canonical entity and may be standalone or belong to a Programme/Challenge.

```text
Programme / Challenge
   ├── Structure / Journey
   ├── Event / Activity
   ├── Registration/Application Configuration
   ├── Operating Team / Role Assignments
   ├── Applications / Participants
   └── Outcomes
```

### Why
BA/business rules treat Programme/Challenge as sharing lifecycle, organizer relations, publication, applications and outcomes. The latest WF04 also describes a shared flow: list → create → basic info → journey → activities/events → registration/access → operating roles → draft/publish → manage/monitor → detail.

### Consequence for code
- One module: `programme`.
- One root table/entity for Programme.
- Type-specific child records are allowed.
- Do **not** duplicate Programme and Challenge service layers.

**Freeze:** `ACCEPTED`.

## D2 — P0 HUB/Chapter/CLB linkage

### Decision
For the 29/09 soft-launch cohort use **pre-seeded confirmed network relationships as the primary path**.

The known roster is imported before go-live as invitation/bootstrap data. When a user creates an account with a matching normalized email, the system attaches the intended confirmed relationship(s).

```text
Known HUB roster
   ↓ import
MembershipInvite / Bootstrap record
   ↓ exact account match
IndividualProfile
   ├── CommunityMembership = ACTIVE
   └── LeadershipRecord = ACTIVE   [when applicable]
```

If there is no matching pre-seeded relationship, a user's self-selected HUB/Chapter/CLB **must not become ACTIVE automatically**. The fallback is:

```text
self-selection → CommunityMembership = PENDING_APPROVAL
```

This fallback must not block completion of the P0 profile.

### P0 UI rule
- If matched: show confirmed network context.
- If not matched: allow declaration/request, display pending state.
- No full membership approval workflow is required in the member-facing P0 happy path.

### Data rule
Do not create a permanent generic `Affiliation` object that bypasses Membership/Leadership.

**Freeze:** `PRESEED + PENDING FALLBACK`.

## D3 — P0 Profile Completion policy

### Decision
Profile completion is a **derived score from 10 canonical profile groups**, each worth 10 points. It is independent from profile lifecycle status.

| Group | Completion rule | Weight |
|---|---|---:|
| 1. Full name | non-empty | 10 |
| 2. Avatar | valid asset attached | 10 |
| 3. Current role/headline | non-empty | 10 |
| 4. Region | controlled value selected | 10 |
| 5. Short bio | non-empty | 10 |
| 6. Domain / area of interest | >= 1 controlled value | 10 |
| 7. Skills | >= 1 controlled value | 10 |
| 8. Experience | >= 1 experience item OR explicit `NO_EXPERIENCE_YET` | 10 |
| 9. Development goal | non-empty | 10 |
| 10. Current need | non-empty | 10 |

```text
completion_percent = completed_groups * 10
```

### Roadmap metric
`profile_completed_80 = completion_percent >= 80`

### Activation minimum
A Profile can become `ACTIVE` before reaching 80%. Minimum P0 activation is:

- valid account;
- full name;
- region;
- required Terms/Privacy acceptance.

The 80% threshold is a **product KPI**, not an authentication/access gate.

### Why
The BA describes core profile data as basic information, region, domain, skills, experience, goal and need, while the P0 roadmap explicitly measures the percentage of fields completed. Group-based scoring is stable when individual form fields evolve and prevents a long bio or many skills from artificially inflating completion.

**Freeze:** `10 GROUPS / EQUAL WEIGHT`.

## D4 — P0 Consent & Visibility configuration

### Decision
Separate **legal acceptance**, **privacy/processing consent**, and **profile visibility**. Do not represent them as one boolean.

### Required P0 records

1. `TERMS_ACCEPTANCE`
   - required to use the service;
   - versioned document identifier;
   - accepted timestamp;
   - actor/account reference.

2. `PRIVACY_DATA_PROCESSING`
   - required for the P0 profile/data-processing scope;
   - versioned policy identifier;
   - purpose/scope reference;
   - accepted timestamp;
   - revocation/withdrawal semantics where applicable.

### Visibility is not consent
P0 supports visibility configuration as a separate setting. Canonical levels remain:

```text
PUBLIC
NETWORK_ONLY
PROGRAMME_ACCESS
GRANTED_ACCESS
PRIVATE
```

P0 UI does **not** need to expose every future access scenario. It may expose only approved profile groups while backend stores the canonical level model.

### Explicitly excluded from P0 legal model
- investor-specific deep-data grants;
- dataroom grants;
- marketing consent;
- identity-document consent;
- one-off partner data sharing.

Those become separate future `ConsentRecord`/`AccessGrant` records.

### Governance
Any change to Terms/Privacy version, visibility or consent must create an audit event.

**Freeze:** `VERSIONED REQUIRED ACCEPTANCE + SEPARATE VISIBILITY`.

## D5 — Controlled Vocabulary seed

### Decision
Freeze the **taxonomy types, ownership and behaviour now**; literal item lists remain configurable launch data rather than code constants.

### P0 required vocabularies

```text

```

### Schema ready / later

```text
STARTUP_STAGE
ORGANIZATION_TYPE

PROGRAMME_TYPE
EVENT_TYPE

```

### Rules
- Platform Admin owns vocabulary lifecycle.
- Search/filter fields must reference vocabulary item IDs, not raw text.
- Items have `ACTIVE | ARCHIVED` state; historical relations remain valid after archive.
- UI may offer `OTHER` only as a staging value. Free-text suggestions are not immediately searchable canonical taxonomy until curated.
- Initial P0 values are imported from HUB's approved current taxonomy/design dataset before go-live.
- Region seed must use the launch-approved administrative list; do not hard-code it in frontend code.

### Why
BA requires centrally managed vocabularies for filtering/matching. Keeping the actual item set data-driven allows HUB to clean its taxonomy without schema/code changes.

**Freeze:** `SCHEMA + GOVERNANCE FROZEN; VALUES CONFIGURABLE`.
